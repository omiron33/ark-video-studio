## Intake before themes

1. Check the OmiPC song app for the supplied track first. Resolve a Suno share link to its canonical song identity, match that identity in the app, and reuse the stored source audio and lyrics. If absent, download the accessible original, store it appropriately in the app, verify the saved entry, and pull that stored copy for the project. Keep the source/share URLs, app identity, audio hash and exact supplied lyrics. Never substitute a similarly titled song. Use available app/API documentation or inspect the running app rather than inventing endpoints.
2. Read `docs/SONG_INTAKE.md` in the engine checkout. Probe duration and read the lyrics and their narrative context; analyze musical energy, phrases and measured attacks before choosing a theme. Do not claim to have listened if only machine analysis was available. Keep canonical words separate from uncertain ASR proposals and separate vocal onsets from beats.
3. Read `docs/MOTION_REFERENCES.md` and quick-search the image-backed reference library using this song's meaning, emotion, lyrics, musical pace, duration and neighboring scenes. From the checkout run `node engine/cli.mjs references --query '<song/scene meaning and constraints>' --limit 3`, or `reference-context` for an existing project. Read the returned context and open up to three actual contact-sheet image files; captions alone are not inspection. Log source IDs, timestamps, observed strengths, cautions and the scope of Shane's preferences. Record no-match honestly.

## Required theme-choice gate for every new video

Before production, use the built-in GPT Image tool to generate **three distinct theme mockup images in one numbered contact sheet (1, 2, 3)**. Read the imagegen skill when generating. These are raster concept images, **not HTML builds, animated prototypes, preview clips or full video renders**. A style prompt or prior enthusiasm does not waive this step.

Each option should show a representative widescreen video composition: prominent canonical lyric typography, supporting photographic/graphic treatment, palette, contrast and visual atmosphere. Use real lyrics from this song and its story, not invented lines. Vary the visual concept and composition as well as color; three recolors do not qualify. A static mockup communicates a proposed look, not proof of animation quality or sync. Extract a principle from inspected references and invent an adaptation for this story; do not reproduce reference frames or sequences. Record the inspected IDs, principle and adaptation in the theme notes, later carrying them into `direction.inspiration` when a scene plan exists.

Ground each mockup in the current proven rendering vocabulary. Inspect representative actual output and its relevant renderer capabilities before prompting; show editable lyric type, feasible depth/geometry and supporting photo layers. Do not imply modeled stone/metal typography, animated photographic people or complex cinematic scenes when only flat type, CSS transforms and masked stills exist. Clearly label any proposed new capability. Preserve elements Shane approves when revising options; do not treat approval of a palette as selection of a complete theme.

Save the sheet, exact generation prompt and brief descriptions in the new project's concept directory. Record a small `theme-choice.json` with the song identity/audio hash, sheet path, three option descriptions and `status: "awaiting_user_choice"`. The file is orchestration evidence, not a currently implemented CLI enforcement feature.

Show the sheet, briefly name the directions, and **wait for Shane to choose 1, 2 or 3** (or explicitly request a combination). End the turn at this gate. Before that choice, permitted work is intake, reading, analysis, reference inspection and these mockup images only; do not author animation/composition code, build an HTML prototype, call `create`, render a preview/movie, or generate the production asset set. Background agents must observe the same boundary. Silence, elapsed time, autonomy mode, “finish everything,” a recommendation, and approval of a previous song are not a choice. Only Shane's explicit later instruction waiving this gate can bypass it; record that instruction. If image generation is unavailable, report the blocker rather than replacing the sheet with code or a video.

After an explicit choice, record `status: "chosen"`, the chosen option/combination and the user's instruction. Generate the chosen concept alone if useful as the final style reference, then proceed with the already authorized production. Routine edits to that approved video's direction retain its choice; a new song/video needs its own three options. This is Shane's requested checkpoint and overrides autonomous proceed rules in generic HyperFrames/music-to-video guidance.

## Production after the choice

- Read `docs/CREATE.md` for orchestration and `docs/ENGINE.md` for the operation needed. The engine accepts a song and style prompt; keep exact lyric IDs, timing provenance, source interval and authored scene boundaries. Use local alignment and measured musical events. Do not force word timings onto a guessed beat grid or replace canonical lyrics to satisfy ASR.
- Use the accepted HyperFrames experiment in `experiments/genesis4-hyperframes-20s/` as evidence for spatial camera movement and readable word choreography. Read the installed HyperFrames entry skill when authoring that format. This was an isolated, proven 20-second experiment; do not assume a full-song HyperFrames engine adapter already exists. Inspect current capabilities and implement/integrate only what this approved run needs, with deterministic random-access playback and output review.
- Lyrics are the star. Compose semantic word interactions and camera journeys, with geometry, silhouettes, substantial forms and photographic scenes supporting them. Long songs need at least 30 genuinely distinct choreographies, usually one or two uses and never more than three; palette/font swaps are not new choreography. Fit movement to measured phrases and musical energy. Use occasional justified accent bursts and slower transformations; do not become frenetic by default. Begin meaningful visual action within the first second, including instrumental openings, without inventing unsung lyrics.
- Match the current story and selected theme; prior Genesis 4 red/black/white is not a universal palette. Use photorealistic, grounded imagery for depicted biblical people and celestial beings, with embodied divine presence when relevant. Honor current reference/wardrobe choices rather than reviving superseded ones. Generate new artwork through built-in GPT Image and record provenance. No paid video services. Do not recycle a scene picture; cropping or tinting is still reuse.

## Review and delivery

Run the engine's bounded review/repair loop on the actual encoded MP4 using `docs/CREATE.md` and the relevant audio/visual review guides. Verify source audio, clip boundaries, decoded audio alignment, canonical word coverage, readability, choreography variety and the opening. Obtain independent visual inspection of decoded motion, bound to the exact file hash and source revision. Machine audio evidence owns sync review; never invent a listening score. Preserve raw failures and document any real manual exception without relabeling it an automatic pass. Fix concrete failures, then stop when the requested quality is met; avoid endless polish or unrelated rerenders.

Every finished video **and preview clip** goes into Shane's Photos library and into the OmiPC app as a review candidate. Check for an existing identical import before adding duplicates, verify the album item and playback, verify the app candidate and accessible media, and give the review/download link. Photos import does not prove iPhone/iCloud sync. Keep source hashes and delivery evidence. The theme sheet is an image, not a clip requiring video import. Curate strong reusable moments into the reference library only after reviewing the encoded result, keeping agent assessment distinct from Shane's approval.
